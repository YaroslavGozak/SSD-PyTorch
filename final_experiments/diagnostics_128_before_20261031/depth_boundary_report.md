# Етап 2c: валідація межі адаптивної глибини

**Статус: COMPLETE. Рішення за повним набором заданих критеріїв:
поки залишити production-межу 140; універсальну заміну на 128 не схвалювати.**
Це не означає, що стара межа точніша: її провал на 129–140 px підтверджено.
Причина відмови в безумовному схваленні саме кандидата 128 — критерій
еквівалентності L_R=4/5 при 128 px виконується для квадрата, але **не для
прямокутників із min_dim=128**. Висновок залежить від форми ROI.
Production policy та ваги автоматично не змінено.

## 1. Межа 129–131 px

Розміри скрізь **H x W**. mAP і Recall наведено у відсотках.
AP — project area-integral AP@0.5, Recall — macro-average за GT-supported
класами на тому самому confidence threshold, не COCO average recall.

| Input | mAP L4 | mAP L5 | Recall L4 | Recall L5 | Mean raw max conf L4 / L5 | Mean best-anchor IoU L4 / L5 | GT IoU >= 0.5, L4 / L5 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 129x129 | 0.89 | 58.47 | 1.00 | 59.83 | 0.2078 / 0.8845 | 0.4185 / 0.6855 | 23.03% / 89.70% |
| 130x130 | 1.24 | 57.36 | 1.80 | 58.63 | 0.2130 / 0.8904 | 0.4197 / 0.6864 | 23.03% / 89.70% |
| 131x131 | 1.99 | 58.59 | 2.65 | 59.43 | 0.2152 / 0.8939 | 0.4209 / 0.6882 | 23.10% / 89.97% |

L_R=5 стабільно усуває провал вже з 129 px. Повторні controls 132/136/140
дали відповідно 58.80/59.61/60.34% mAP замість 2.37/3.89/2.88% при L_R=4.
Проміжні 133–135/137–139 px окремо не перевірялися.

Для **всіх восьми** прямокутників із min_dim>128 L_R=5 кращий за обома
метриками, в обох орієнтаціях. Нового систематичного падіння через L_R=5
тут немає. Абсолютна різниця між орієнтаціями не є depth regression:
вхідні crops і видимі GT між різними H/W не ідентичні.

Важливий виняток до припущення «при 128 px достатньо L_R=4»:
для обох прямокутників із min_dim=128 L_R=5 теж суттєво кращий
(+12.08/+10.28 в.п. mAP, +10.38/+11.76 в.п. Recall).
Для **128x128** controls натомість точно еквівалентні:
42.74% mAP, 45.51% Recall при L_R=4 і 5.
Кандидат із межею 128 залишив би обидва прямокутники на гіршому L_R=4.
Це **залишкове обмеження кандидата, а не нова регресія проти старої policy**:
обидва правила вибирають L_R=4 при min_dim=128.

## 4. Рішення за критеріями

| Критерій | Висновок |
|---|---|
| L5 кращий на 129–140 px | PASS на всіх перевірених квадратах 129/130/131/132/136/140 |
| Немає нового падіння на rectangles min_dim>128 | PASS: 8/8 пар кращі за mAP і Recall |
| Узгоджені anchors/predictions | PASS: 9472/9472 forwards |
| При 128 px L4 не гірший / еквівалентний L5 | PASS лише для 128x128; FAIL для 128x160 та 160x128 |
| Немає підстав додавати L6 при 144+ | Для перевіреного 144x144 підстав немає: mAP 59.60% -> 59.38%, Recall незмінний; вищі розміри й прямокутники на L6 не оцінювалися |

**Однозначна рекомендація для загальної production policy: поки залишити
стару межу 140**, дотримуючись вимоги не схвалювати універсальне min_dim-rule
за неоднозначного перенесення квадратного висновку на прямокутники.
Це консервативний no-go саме за повним набором критеріїв, не заперечення
великого виграшу L5 на 129–140 px.

Для окремого наступного CPU-pilot на **перевірених buckets** дані підтримують
L5 для всіх перевірених форм із min_dim>=128; для 128x128 L4 можна залишити,
оскільки L5 не додає точності. Таку bucket/shape-aware policy слід оформляти
окремо, а не маскувати як уже перевірену універсальну функцію лише від min_dim.
Межа 127 також дала б L5 всім перевіреним inputs і не погіршила б 128x128,
але сама нова межа 127/128, менші inputs і прямокутники з min_dim=127
не перевірені: **127 не рекомендується як доведена альтернативна межа**.

Оскільки загальну зміну правила не схвалено, новий production-варіант
`get_max_feature_layer_by_roi_size()` у цьому звіті не пропонується.
Наявна функція з межею 140 залишається незмінною. Наступна перевірка має
зосередитися на shape-aware винятку для min_dim=128 або нижчій межі з
контролями нижче 128, після чого потрібні CPU backend parity та latency.
Цей запуск не оцінює CPU/Raspberry Pi latency, tracker чи незалежний test split.
